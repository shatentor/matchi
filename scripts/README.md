# scripts

Служебные скрипты Matchi.

| Файл | Что делает |
|---|---|
| `smoke_check.py` | ~90 проверок кода без БД: импорты, роутеры, фильтры, клавиатуры, SQL |
| `backup_db.sh` | резервная копия базы (формат custom), проверка дампа и ротация |
| `restore_db.sh` | восстановление дампа в **указанную** базу с подтверждением |

Доступы оба bash-скрипта читают из `.env` в корне проекта (`DB_USER`, `DB_PASSWORD`, `DB_HOST`,
`DB_PORT`, `DB_NAME`, `BACKUP_DIR`, `BACKUP_KEEP`, `PG_BIN_DIR`). Переменные окружения имеют
приоритет над `.env` — так удобно снимать бэкап другой базы, не правя файл. Пароль передаётся
только через `PGPASSWORD` в окружении процесса: в аргументах командной строки он был бы виден
любому пользователю системы в `ps`.

Значения по умолчанию совпадают с `config/settings.py`: `BACKUP_DIR` =
`~/.local/share/matchi-backups`, `BACKUP_KEEP` = 14, `PG_BIN_DIR` = `/usr/lib/postgresql/16/bin`.
Последнее важно: серверных бинарников PostgreSQL на этой машине нет в `PATH`, поэтому `pg_dump`
и `pg_restore` вызываются по полному пути.

`DB_USER`, `DB_HOST`, `DB_PORT` и `DB_NAME` значений по умолчанию **не имеют** — без них скрипт
падает с ошибкой. Молчаливый дефолт был бы опасен: локальный кластер Matchi слушает **5433**, а
на 5432 висит SSH-туннель к чужой базе, и бэкап «по умолчанию» уехал бы не туда. Если в
настройках всё же оказался порт 5432, скрипты печатают предупреждение.

## Снять бэкап

```bash
./scripts/backup_db.sh
```

Что происходит: `pg_dump -Fc` пишет во временный файл `*.dump.part`, файл проверяется
`pg_restore --list`, и только потом получает финальное имя
`<база>-YYYYmmdd-HHMMSS.dump` в `BACKUP_DIR`. Битый или обрезанный дамп до каталога бэкапов не
доходит — бэкап, который не открывается, хуже отсутствия бэкапа: он создаёт ложную уверенность.
После этого работает ротация: остаются последние `BACKUP_KEEP` файлов, более старые удаляются.

Формат custom (`-Fc`) выбран, потому что он сжат и позволяет восстанавливать выборочно
(например, одну таблицу через `pg_restore -t`), чего простой SQL-дамп не умеет.

Код выхода `0` — бэкап снят и проверен. Любая ошибка (кластер не поднят, неверный пароль, нет
`pg_dump`, пустой или битый дамп, не записался каталог) даёт код `1` и сообщение с причиной.
Проверяйте код выхода в любой автоматизации: успех обязан отличаться от провала.

## Проверить бэкап

Быстро — посмотреть оглавление архива:

```bash
/usr/lib/postgresql/16/bin/pg_restore --list ~/.local/share/matchi-backups/<файл>.dump | head -20
```

Это `backup_db.sh` делает сам при каждом запуске. Но `--list` читает только оглавление, а не
данные, поэтому **раз в месяц стоит делать настоящую проверку — восстановление в отдельную
базу** и сравнение чисел с рабочей:

```bash
DUMP=$(ls -t ~/.local/share/matchi-backups/*.dump | head -1)
echo yes | ./scripts/restore_db.sh "$DUMP" matchi_restore_test
/usr/lib/postgresql/16/bin/psql -h 127.0.0.1 -p 5433 -U postgres -d match_bot \
  -Atc "select count(*) from users" -c "select count(*) from posts"
/usr/lib/postgresql/16/bin/dropdb -h 127.0.0.1 -p 5433 -U postgres matchi_restore_test
```

`restore_db.sh` сам печатает число таблиц и строк в `users`/`posts` в восстановленной базе —
остаётся сверить их с выводом второй команды. Пароль запросит `psql`; чтобы не вводить руками,
экспортируйте `PGPASSWORD` в текущей сессии.

## Восстановить

```bash
./scripts/restore_db.sh <файл.dump> <имя_целевой_базы>
```

Целевая база — **обязательный аргумент**, из `.env` она не берётся, и скрипт требует ввести
`yes`. Это защита от опечатки, которая затрёт рабочую базу. Восстановление прямо в рабочую базу
(`DB_NAME` из `.env`, то есть `match_bot`) отдельно запрещено; если это осознанное
восстановление после аварии — `ALLOW_PROD_RESTORE=yes ./scripts/restore_db.sh ...`, и лучше
сначала снять свежий бэкап того, что есть.

Если целевой базы нет, скрипт её создаёт. Дамп проверяется `pg_restore --list` **до** вопроса
и до любых изменений, так что битым файлом содержимое целевой базы не затрёшь.
Восстановление идёт с `--clean --if-exists --no-owner --no-privileges --exit-on-error`:
объекты заменяются, владельцы и гранты берутся из целевого кластера, а первая же настоящая
ошибка останавливает процесс, а не проглатывается.

Бот на время восстановления рабочей базы надо остановить: он держит пул соединений, а `DROP`
объектов при активных запросах даёт блокировки и половинчатое состояние.

## Cron: ежедневный бэкап

```crontab
30 3 * * * /home/nikita/PycharmProjects/matchi/scripts/backup_db.sh >> /home/nikita/.local/share/matchi-backup.log 2>&1
```

Ставится через `crontab -e`. Пути в строке абсолютные: `cron` запускает задание с урезанным
окружением и без `cd` в проект. Скрипт это учитывает — он сам находит корень проекта
относительно своего расположения и читает оттуда `.env`.

Если в crontab указать `MAILTO=`, при ненулевом коде выхода `cron` пришлёт письмо с текстом
ошибки. Без почты смотрите хвост лога: `tail -20 ~/.local/share/matchi-backup.log`. Лог сам не
чистится — при желании добавьте его в `logrotate` или обрезайте вручную.

## Бэкап на той же машине — это ещё не бэкап

`BACKUP_DIR` лежит на том же диске, что и сам кластер PostgreSQL. От случайного `DROP COLUMN`,
неудачной миграции или `DELETE` без `WHERE` это спасает, а от смерти диска, потери или кражи
ноутбука, шифровальщика и ошибочного `rm -rf` — нет: копия исчезнет вместе с оригиналом.
Правило «3-2-1» (три копии, два носителя, одна вне помещения) здесь не выполнено ни по одному
пункту.

Поэтому дамп надо регулярно уносить наружу — на внешний диск, другой сервер или в объектное
хранилище, например:

```bash
rsync -av ~/.local/share/matchi-backups/ backup-host:/srv/matchi-backups/
```

Дампы содержат персональные данные участников (имена, города, описания, переписку и
`file_id` фотографий), поэтому каталог создаётся с правами `700`, файлы — `600`. Наружу их
стоит отправлять только по шифрованному каналу и хранить в зашифрованном виде
(`gpg -c`, зашифрованный том, шифрование на стороне хранилища).

## Проверено

`backup_db.sh` и `restore_db.sh` прошли `shellcheck` (0.11.0) без замечаний. Проверялось на
живой базе: снятие дампа, восстановление в отдельную базу `matchi_restore_test` с построчным
сравнением всех 23 таблиц, ротация на `BACKUP_KEEP + 3` файлах, код выхода `1` при недоступном
порте и неверном пароле, отказ принять мусор вместо дампа и отсутствие пароля в аргументах
процессов, выводе и логе.
