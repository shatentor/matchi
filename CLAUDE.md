# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Matchi — Telegram-бот знакомств (`@match_botbot`): анкета, поиск людей по полу, возрасту и общим интересам, лайки/дизлайки, взаимные лайки, личные переписки, рулетка случайных собеседников по интересу, групповые комнаты по интересам, жалобы и админ-панель. aiogram 3.30, Python 3.12, PostgreSQL (asyncpg), Redis (FSM, очереди рулетки, троттлинг), Pydantic v2.

## Язык и стиль

Отвечай пользователю по-русски. Комментарии в коде, докстринги и все тексты сообщений бота — тоже по-русски.

В проекте исторически много комментариев-пометок вида `# ИСПРАВЛЕНО`, `# ИМПОРТИРУЕМ`, `# Убрал state="*"`, `# <-- Изменено`. Новые такие не добавляй, а встреченные при правке удаляй. Комментарий нужен только там, где код не может сам сказать о внешнем ограничении (лимит Telegram, UNIQUE в схеме, порядок регистрации хендлеров).

## Запуск и окружение

```bash
.venv/bin/python main.py                  # запуск бота (только из корня проекта)
.venv/bin/python db/migrate.py            # применить миграции схемы (идемпотентно)
.venv/bin/python db/migrate.py --status    # посмотреть, какие миграции применены
.venv/bin/python create_db_tables.py      # устаревший путь: только базовые семь таблиц
```

**Схема меняется только миграциями.** Файлы `db/migrations/NNN_название.sql` применяются по порядку номеров, учёт — в таблице `schema_migrations`. `create_db_tables.py` и `db/sql_templates.sql` оставлены для совместимости и описывают лишь исходные семь таблиц; новые изменения туда не добавляй.

Запускать строго из корня: пакеты живут без `__init__.py` (namespace packages), из другой директории импорты не разрешатся.

Перед запуском нужны PostgreSQL с созданной БД, Redis и `.env` в корне. `BOT_TOKEN` обязателен — без него падает уже импорт `config/settings.py`. Отсутствие `ADMIN_IDS` даёт только предупреждение, но ломает жалобы и `/support` (уведомлять некого).

Переменные окружения (все в `config/settings.py`): `BOT_TOKEN`, `ADMIN_IDS` (через запятую, без пробелов), `DB_USER`/`DB_PASSWORD`/`DB_HOST`/`DB_PORT`/`DB_NAME`, `REDIS_HOST`/`REDIS_PORT`/`REDIS_DB`, `MIN_AGE` (18), `MAX_AGE` (99), `CANDIDATES_LIMIT` (50), `SUPPORT_COOLDOWN` (120), `BROADCAST_DELAY` (0.05). Лимиты `MAX_NAME_LENGTH`, `MAX_DESCRIPTION_LENGTH`, `MAX_PHOTOS` заданы в том же файле константами.

**Локально всё поднято, но вручную.** PostgreSQL 16 в системе есть, только серверные бинарники лежат в `/usr/lib/postgresql/16/bin` и в PATH не попадают — `which postgres` их не находит, зови по полному пути. Кластер поднят без sudo: данные в `~/.local/share/matchi-pg`, порт **5433**, суперпользователь `postgres`, база `match_bot`, все миграции применены. Порт 5432 занят SSH-туннелем к рабочей базе — **не подключайся к нему и не выполняй там запросов**, именно поэтому кластер живёт на 5433. Redis взят из pip-пакета `redislite` (внутри лежит собранный `redis-server`) и слушает 6379, данные в `~/.local/share/matchi-redis`. Это компромисс для локальной разработки: `apt install redis-server` требует sudo, зато дал бы автозапуск через systemd. Зависимости стоят в постоянном `.venv`, бот запускается как `.venv/bin/python main.py`, лог пишется в `~/.local/share/matchi-bot.log`.

Ни кластер, ни Redis не поднимаются после перезагрузки сами — поднимай их так:

```bash
/usr/lib/postgresql/16/bin/pg_ctl -D /home/nikita/.local/share/matchi-pg \
  -o "-p 5433 -k /home/nikita/.local/share/matchi-pg-run -h 127.0.0.1" \
  -l /home/nikita/.local/share/matchi-pg.log start
.venv/lib/python3.12/site-packages/redislite/bin/redis-server --port 6379 --bind 127.0.0.1 \
  --dir /home/nikita/.local/share/matchi-redis --dbfilename matchi.rdb \
  --logfile /home/nikita/.local/share/matchi-redis/redis.log --daemonize yes
```

Пути в `-o` подставлены целиком: PostgreSQL получает эту строку как аргументы сервера, и `~` в ней никто не раскроет.

Таблица `stickers` (стикер за взаимный лайк) ничем не заполняется автоматически — `StickerRepository.add_sticker` не вызывается нигде. Если таблица пуста, взаимный лайк работает, просто без стикера. Заполняется вручную: `INSERT INTO stickers (lovely) VALUES ('<file_id>');`.

## Проверка изменений

Тестов, линтеров, CI, pre-commit и Dockerfile в проекте **нет** — не предлагай `pytest`/`ruff` как существующие команды. Вместо этого:

```bash
.venv/bin/python scripts/smoke_check.py   # ~90 проверок: импорты, роутеры, фильтры, middleware, клавиатуры, SQL
.venv/bin/python -m compileall -q .       # только синтаксис
```

`scripts/smoke_check.py` работает без БД и без реального токена (подставляет фиктивные значения сам, репозитории получают заглушку пула). Он ловит именно те классы ошибок, которые здесь уже случались: несуществующий метод репозитория, обязательное поле Pydantic, поломанную сборку роутера, несинхронизированные конструкторы сервисов. **Дополняй его при каждом заметном изменении** — это единственная автоматическая защита в проекте. Проверка SQL внутри требует `sqlglot` (в `requirements.txt` его нет, при отсутствии секция пропускается).

## Архитектура

Поток одного апдейта:

```
main.py (сборка DI вручную)
  → UserContextMiddleware (outer!)     middlewares/user_context.py
  → фильтры                            filters/custom_filters.py
  → роутер + FSM-состояние             handlers/*.py
  → сервис (бизнес-логика)             services/*.py
  → репозиторий (весь SQL)             db/repositories/*.py
```

Зависимости собираются руками в `main.py`: пул → репозитории → сервисы → фильтры → классы хендлеров → роутеры. Хендлеры — это классы, которые хранят сервисы в полях и отдают собранный `Router` из `get_router(...)`; регистрация императивная (`self.router.message.register(...)`), декораторов нет. Меняя сигнатуру `get_router` или конструктора хендлера, обязательно правь `main.py`. `Router` создаётся в `__init__`, поэтому повторный вызов `get_router` продублирует все регистрации — вызывать его можно один раз.

Инстанс `Bot` попадает в хендлеры двумя разными способами: `ProfileSearchHandlers` и `AdminHandlers` получают его через `set_bot_instance()` из `main.py` (отсюда проверки `if not self.bot`), а `CommandHandlers` берёт из `message.bot`. Второй способ правильный — aiogram сам передаёт `bot` в хендлер; при рефакторинге этих классов сеттер можно убрать.

**`UserContextMiddleware` зарегистрирован как `outer_middleware` намеренно.** Inner-middleware выполняется уже после фильтрации, поэтому только outer успевает положить пользователя в контекст до фильтров. Фильтры получают его в аргументе `user`, потому что aiogram передаёт значение из `data` в параметр фильтра **с тем же именем** — связь держится на совпадении строки `"user"`, и при переименовании ключа фильтры молча уйдут в резервную ветку с запросом к БД (поведение сохранится, просядет только производительность). Потребители — `IsRegistered` и `IsFeedbackForCurrentProfile`; `IsAdmin` в БД не ходит вообще. Резервный путь с запросом к БД в фильтрах не убирай: он спасает, когда `user` пришёл `None` из-за недоступности БД.

**Порядок включения роутеров в `main.py` значим** — aiogram резолвит их в порядке подключения, и первое совпадение останавливает поиск. Регистрация идёт первой (её состояния владеют вводом анкеты), меню — сразу вторым, перед командным роутером: `/menu` и коллбэки меню должны доставаться меню раньше, чем их перехватит состояние или catch-all нижнего роутера, иначе единственный универсальный вход в бота окажется недоступен именно тогда, когда он нужнее всего. Админский роутер идёт последним, роутер ошибок — после всех. Отсюда два правила, которые надо держать при любой правке хендлеров:

- **Каждый текстовый хендлер состояния закрыт фильтром `not_command` (`~F.text.startswith("/")`)** — во всех роутерах, не только в регистрации. Без него состояние роутера, подключённого выше, съедает команды роутеров ниже: `/start` на шаге города записался бы как название города, `/searchi` во время смены имени стал бы новым именем, а любая команда в состоянии админской рассылки уехала бы текстом всем пользователям. Добавляешь новое текстовое состояние — добавляй и этот фильтр.
- **Fallback-хендлеры** («пришлите текст», «нажмите кнопку») регистрируются **после** основных хендлеров того же состояния, иначе перехватывают корректный ввод. Ловят они только нетекстовые сообщения, чтобы команды по-прежнему проваливались дальше по цепочке роутеров.

Побочный эффект: неизвестная команда внутри состояния не обрабатывается никем и бот молчит. Это принятый компромисс — закрывается общим catch-all в командном роутере, если понадобится.

FSM хранится в Redis, поэтому состояния переживают перезапуск бота, но теряются при очистке Redis. Группы состояний: `Register` (10 шагов анкеты, `handlers/registration.py`), `ChangeProfileStates` (редактирование, `profile_management.py`), `ProfileSearchStates` (просмотр анкет, сообщение, жалоба, `profile_search.py`), `CommandsStates` (текст в поддержку, `commands.py`), `AdminStates` (рассылка, `admin.py`), `DialogStates` (активная переписка, `dialogs.py`), `RoomStates` (нахождение в комнате, `rooms.py`).

Три состояния релеят чужой ввод дальше — админская рассылка, диалог и комната. Для них правило про `not_command` не стилистическое, а защитное: без него команда уедет текстом собеседнику, всем участникам комнаты или всем пользователям бота. Проверять это надо имитацией роутинга на **настоящих** объектах `aiogram.types.Message`: фильтр `Command` начинается с `isinstance(message, Message)`, поэтому на самодельной заглушке он молча не срабатывает и тест выглядит зелёным, ничего не проверив.

`callback_data` собирается сырой склейкой префикса и `tg_chat_id`: `like<id>`, `dislike<id>`, `message<id>`, `complain<id>`, `yes<id>`, `no<id>`, а также `city_<название>` и `change_photo_one`/`add_photo_two`/`delete_photo_three`. Схема хрупкая, и её ловушки держатся на неочевидных страховках:

- **`"message"` — префикс `"message_to_all"`.** Хендлер анкеты висит на `F.data.startswith("message")` в роутере, который подключён раньше админского, поэтому кнопку рассылки «Message to all users» спасает только `StateFilter` на обоих хендлерах. Уберёшь состояние — админская рассылка перестанет открываться.
- **`"change_photo"` — префикс `"change_photo_one"`.** Разведено точным `F.data == "change_photo"`, зарегистрированным раньше `startswith`-варианта.
- **`"no"`** сейчас ни с чем не конфликтует, но `handle_yes_or_no_callback` зарегистрирован без `StateFilter` и перехватит любой будущий `none`/`notify_*` в любом состоянии.
- **`"like"` — суффикс `"dislike"`.** При `startswith` порядок проверок фактически не важен, но ветку `dislike` держат первой: порядок станет критичным, если проверка сменится на вхождение подстроки или на `removeprefix` без `startswith`.

При добавлении новых кнопок лучше заводить `CallbackData`-фабрику aiogram, чем наращивать префиксы — так сделано в `keyboards/menu.py`.

### Инлайн-меню

`/menu` (`handlers/menu.py`, `keyboards/menu.py`) — единая точка входа вместо длинного списка команд. Кнопки описаны фабрикой `MenuCB(CallbackData, prefix="menu")` с единственным полем `action`. Экранов два: `main_menu_keyboard()` (поиск, переписки, рулетка, комнаты, профиль, интересы) и `extra_menu_keyboard()` (взаимные лайки, изменение профиля, письмо админу, помощь); действия `extra` и `main` переключают их через `edit_text`, чтобы не плодить сообщения в чате.

`MenuHandlers` — хаб, а не копия логики: он получает в конструктор экземпляры остальных классов хендлеров (поэтому в `main.py` они теперь лежат в переменных, а не создаются на месте вызова `get_router`) и зовёт их существующие точки входа — `start_searching_profiles`, `cmd_dialogs`, `cmd_roulette`, `rooms_command`, `show_profile_func`, `show_interests`, `show_mutual_liked`, `change_profile_command`, `support_create`, `help_func`. Держится это на одном свойстве: все перечисленные методы читают `message.chat.id`, а не `message.from_user`, а в личке `chat.id` совпадает с id пользователя — поэтому передать в них `call.message` (сообщение, отправленное от имени бота) безопасно. **Появится в такой точке входа обращение к `message.from_user` — вызов из меню молча начнёт работать от имени бота**, без ошибки и без пустого ответа. Значит либо не добавляй туда `from_user`, либо принимай id отдельным аргументом.

Меню сделано инлайновым намеренно. Кнопки reply-клавиатуры отправляют обычный текст, и он попадал бы в текстовые состояния FSM: на шаге ввода имени нажатие «🔍 Искать людей» записалось бы как имя, а в переписке и в комнате уехало бы собеседнику и всем участникам. Инлайн-кнопки текстом не являются, поэтому конфликта нет. Постоянная reply-клавиатура в проекте всё же используется — в режиме диалога (`keyboards/reply.py`); это осознанное исключение: там она должна оставаться под рукой всю переписку, а её кнопки обрабатываются до релея.

`set_commands` публикует в меню Telegram всего четыре команды — `/menu`, `/searchi`, `/start`, `/help`. Одиннадцать пунктов приходилось листать, а все разделы и так доступны кнопками. Остальные команды не удалены и работают, если набрать их руками, — они просто не подсказываются. Админские `/admin`, `/complains` и команды комнат не публикуются по-прежнему.

### Переписки, рулетка и комнаты

Три фичи поверх анкет, у них общий механизм — релей: бот пересылает чужие сообщения, а не даёт участникам прямой контакт.

**Личные диалоги** (`handlers/dialogs.py`, `services/dialog_service.py`, таблица `dialogs`). Состояние `DialogStates.active` с `peer_id`: весь текст пересылается собеседнику, в БД сообщение кладётся plain-текстом, адресату уходит `message.html_text`. Пара в `dialogs` хранится упорядоченной — этого требует `CHECK (user_one < user_two)`, поэтому любой метод репозитория сортирует пару сам (сравнением строк!), а частичный уникальный индекс не даёт открыть два активных диалога на одну пару. Постоянная reply-клавиатура из `keyboards/reply.py` («Завершить», «Профиль», «Пожаловаться») обрабатывается **до** общего релея, иначе её текст уедет собеседнику.

**Рулетка** (`services/roulette_service.py`). Очередь ожидания по интересу в Redis, ключ `roulette:queue:<interest_id>`. Выдача из очереди обязана быть атомарной (`LPOP`), иначе одного ожидающего сведут сразу с двумя; вытащенный участник дополнительно проверяется на «уже в диалоге». Сведённая пара открывает обычный диалог с `source="roulette"`.

**Комнаты** (`handlers/rooms.py`, `services/room_service.py`, таблицы `rooms`, `room_members`, `room_messages`, `room_bans`). Два режима, и разница принципиальная:

- `mode='relay'` — бот сам рассылает сообщение всем участникам. Веер идёт **только через `Outbox`** (`services/outbox.py`), никогда прямым `bot.send_message` в цикле: Telegram не даёт боту больше ~20 сообщений в минуту в один групповой чат и порядка 30 в секунду суммарно, а за превышение прилетает флуд-контроль на весь бот. Отсюда и лимит `ROOM_MEMBER_LIMIT` = 30 участников.
- `mode='native'` — комната привязана к реальной супергруппе (`rooms.tg_chat_id`), бот только выдаёт одноразовые ссылки через `create_chat_invite_link`. **Бот не может создать супергруппу сам** — её создаёт человек, добавляет бота админом и вызывает в ней `/room_bind <room_id>`. Для живых и больших комнат это правильный путь: доставку, историю и уведомления берёт на себя Telegram.

`Outbox` соблюдает `OUTBOX_RATE` в секунду суммарно и `OUTBOX_PER_CHAT_INTERVAL` на один чат, отправляет через `send_with_retry` (в отличие от `safe_send_*` он ретраит `TelegramRetryAfter`), а при неустранимой ошибке доставки зовёт `RoomService.handle_undeliverable`, который исключает участника из комнат. Зависимость между ними взаимная, поэтому в `main.py` сервис создаётся первым, а `room_service.outbox` присваивается после создания очереди. Очередь надо `start()` перед поллингом и `stop()` в `finally` **до** закрытия сессии бота и пула БД.

**Интересы** (`handlers/interests.py`, таблицы `interests`, `user_interests`) — это ещё и вход в подбор: `get_candidate_ids` ранжирует кандидатов по числу общих интересов (`ORDER BY common DESC, RANDOM()`). Это ранжирование, а не фильтр: кандидат без общих интересов обязан остаться в выдаче, иначе при незаполненных интересах поиск вернёт ноль анкет.

### Модель данных

Таблицы (`db/sql_templates.sql`): `users`, `descriptions`, `stickers`, `likes`, `dislikes`, `messages`, `complains`. Неочевидное:

- `tg_chat_id` хранится **строкой** (`VARCHAR(20)`), а Telegram API отдаёт `int`. Код постоянно конвертирует туда-обратно: репозитории принимают `str`, хендлеры получают `int`. Это главный источник опечаток — сервисы приводят к `str` сами, поэтому в новые методы сервисов передавай `int`, а в репозитории `str`.
- Описание профиля лежит **не** в `users`, а в отдельной таблице `descriptions` 1:1. Поэтому `get_user_profile_data()` делает второй запрос и возвращает `None`, если описания нет.
- Фотографии — три отдельные колонки `photo_link`, `photo_link_two`, `photo_link_three`, и раскладка по «слотам» размазана по `user_service`, `profile_management` и `keyboards/inline`.
- `users.tg_username` объявлен `UNIQUE` — обновление занятого кем-то юзернейма даёт `UniqueViolation`, это учтено в middleware.
- `BaseRepository.get_by_id()` строит `WHERE id = $1`; у `users`, `likes`, `dislikes` такой колонки нет. `UserRepository` метод переопределяет, остальные его просто не вызывают.

### Подбор анкет

`MatchingService.get_profiles_for_user()` → `UserRepository.get_candidate_ids()` — **один** SQL-запрос: статус `yes`, исключение себя, диапазон возраста, пол (`Any` отключает фильтр), наличие описания, `NOT EXISTS` по `likes` и `dislikes`, `ORDER BY RANDOM() LIMIT`. Раньше здесь была выборка всех пользователей и по два запроса на каждого — не возвращайся к перебору в Python, добавляй условия в SQL.

Осознанные ограничения текущего подбора: город собирается, но в отборе **не участвует**; фильтрация односторонняя — учитываются только предпочтения ищущего, не встречные; дизлайк вечен, снять его нельзя. Асимметрия справочников: свой пол пишется как `Male/Female/Other`, а предпочитаемый — как `Male/Female/Any`, поэтому пользователя с `gender='Other'` найдёт только тот, кто выбрал `Any`. Список кандидатов перезапрашивается после каждого лайка (новый `RANDOM()`), так что «Профили закончились» означает «запрос вернул ноль строк», а не исчерпание какого-то курсора.

Индексов кроме первичных ключей в схеме нет, хотя взаимные лайки джойнят `likes` по `liked_chat_id` — на росте базы это первое место, где понадобится индекс.

ID показанной анкеты дублируется: `users.last_shown_profile` в БД (его читает фильтр `IsFeedbackForCurrentProfile`) и `shown_profile_id` в FSM-данных (его читают хендлеры). При правке этого места помни про оба места, они могут разойтись.

## Правила, которые легко нарушить

1. **Бот работает с `parse_mode="HTML"`.** Любой текст пользователя (имя, город, описание, причина жалобы, юзернейм) при подстановке в сообщение обязан идти через `escape()` из `utils/text.py`, иначе символ `<` или `&` даёт `TelegramBadRequest: can't parse entities`. Для пересылки чужого текста используй `message.html_text` — он сохраняет форматирование и экранирует остальное. `parse_mode="MARKDOWN"` не применяй: пользовательский текст с `*` или `_` ломает разбор.
2. **Отправка чему-либо другому пользователю — только через `utils/telegram.py`.** Для уведомлений хватает `safe_send_message` / `safe_send_media_group` / `safe_send_sticker`: они глотают `TelegramAPIError` и возвращают `bool`, потому что заблокировавший бота получатель не должен ронять сценарий инициатора. Для **релея чужого сообщения** нужен `send_with_retry` — он пережидает `TelegramRetryAfter` и повторяет, иначе написанное человеком сообщение потеряется молча. Для веерной рассылки — только `Outbox`, никогда цикл по получателям.
3. **Никаких магических чисел** для возраста, длины имени/описания и числа фото — только `settings.*`. Минимальный возраст 18 стоит осознанно: это бот знакомств.
4. **SQL живёт только в репозиториях.** Сервисы и хендлеры не должны обращаться к `pool` напрямую (раньше `MatchingService` это делал).
5. Все состояния FSM должны иметь выход: если шаг ждёт текст — фильтр `F.text` плюс `not_command` плюс fallback на остальные типы; если ждёт кнопку — fallback на текст. Проверяй это имитацией роутинга, а не на глаз: состояние без выхода запирает пользователя молча.

## Чего в проекте нет

Тестов (pytest), линтеров, CI, pre-commit и Dockerfile — нет; единственная автоматическая проверка это `scripts/smoke_check.py`. Нет модерации контента: комнаты и диалоги релеят текст как есть, из инструментов только мьют, бан и жалоба. Нет удаления и редактирования уже разосланных сообщений комнаты — релей односторонний. Нет уведомлений о непрочитанном: диалог живёт только пока пользователь в состоянии `DialogStates.active`.

Мёртвые файлы, которые можно не изучать: `utils/filters.py` и `models/profile.py` (оба пустые, но закоммичены; действующие фильтры — в `filters/custom_filters.py`), каталог `data_base/` (не отслеживается git, остался только старый байт-код). `keyboards/reply.py` больше в этот список не входит — там живёт клавиатура диалога. `.idea/` из индекса git не убран; `__pycache__` из индекса уже вычищены.
