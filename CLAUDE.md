# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Matchi — Telegram-бот знакомств (`@match_botbot`): анкета, поиск людей по полу и возрасту, лайки/дизлайки, взаимные лайки, сообщения незнакомцу, жалобы и админ-панель. aiogram 3.30, Python 3.12, PostgreSQL (asyncpg), Redis (FSM), Pydantic v2.

## Язык и стиль

Отвечай пользователю по-русски. Комментарии в коде, докстринги и все тексты сообщений бота — тоже по-русски.

В проекте исторически много комментариев-пометок вида `# ИСПРАВЛЕНО`, `# ИМПОРТИРУЕМ`, `# Убрал state="*"`, `# <-- Изменено`. Новые такие не добавляй, а встреченные при правке удаляй. Комментарий нужен только там, где код не может сам сказать о внешнем ограничении (лимит Telegram, UNIQUE в схеме, порядок регистрации хендлеров).

## Запуск и окружение

```bash
python main.py                 # запуск бота (только из корня проекта)
python create_db_tables.py     # создать таблицы, идемпотентно (CREATE TABLE IF NOT EXISTS)
```

Запускать строго из корня: пакеты живут без `__init__.py` (namespace packages), из другой директории импорты не разрешатся.

Перед запуском нужны PostgreSQL с созданной БД, Redis и `.env` в корне. `BOT_TOKEN` обязателен — без него падает уже импорт `config/settings.py`. Отсутствие `ADMIN_IDS` даёт только предупреждение, но ломает жалобы и `/support` (уведомлять некого).

Переменные окружения (все в `config/settings.py`): `BOT_TOKEN`, `ADMIN_IDS` (через запятую, без пробелов), `DB_USER`/`DB_PASSWORD`/`DB_HOST`/`DB_PORT`/`DB_NAME`, `REDIS_HOST`/`REDIS_PORT`/`REDIS_DB`, `MIN_AGE` (18), `MAX_AGE` (99), `CANDIDATES_LIMIT` (50), `SUPPORT_COOLDOWN` (120), `BROADCAST_DELAY` (0.05). Лимиты `MAX_NAME_LENGTH`, `MAX_DESCRIPTION_LENGTH`, `MAX_PHOTOS` заданы в том же файле константами.

**Локально нельзя запустить ни бота, ни БД:** сервера PostgreSQL и Redis на машине нет, Docker-демон недоступен. Порт 5432 слушает SSH-туннель к рабочей базе — **не подключайся к нему и не выполняй там запросов.** Значит любая проверка возможна только статическая (см. ниже), а интеграционные сценарии проверяет пользователь у себя.

Таблица `stickers` (стикер за взаимный лайк) ничем не заполняется автоматически — `StickerRepository.add_sticker` не вызывается нигде. Если таблица пуста, взаимный лайк работает, просто без стикера. Заполняется вручную: `INSERT INTO stickers (lovely) VALUES ('<file_id>');`.

## Проверка изменений

Тестов, линтеров, CI, pre-commit и Dockerfile в проекте **нет** — не предлагай `pytest`/`ruff` как существующие команды. Вместо этого:

```bash
python scripts/smoke_check.py   # ~60 проверок: импорты, роутеры, фильтры, middleware, клавиатуры, SQL
python -m compileall -q .       # только синтаксис
```

`scripts/smoke_check.py` работает без БД и без реального токена (подставляет фиктивные значения сам, репозитории получают заглушку пула). Он ловит именно те классы ошибок, которые здесь уже случались: несуществующий метод репозитория, обязательное поле Pydantic, поломанную сборку роутера, несинхронизированные конструкторы сервисов. **Дополняй его при каждом заметном изменении** — это единственная автоматическая защита в проекте. Проверка SQL внутри требует `sqlglot` (в `requirements.txt` его нет, при отсутствии секция пропускается).

## Архитектура

Поток одного апдейта:

```
main.py (сборка DI вручную)
  → UserContextMiddleware (outer!)     middlewares/user_context.py
  → фильтры                            filters/custom_filters.py
  → роутер + FSM-состояние             handlers/*.py
  → сервис (бизнес-логика)             services/*.py
  → репозиторий (весь SQL)             db/repositories/*.py
```

Зависимости собираются руками в `main.py`: пул → репозитории → сервисы → фильтры → классы хендлеров → роутеры. Хендлеры — это классы, которые хранят сервисы в полях и отдают собранный `Router` из `get_router(...)`; регистрация императивная (`self.router.message.register(...)`), декораторов нет. Меняя сигнатуру `get_router` или конструктора хендлера, обязательно правь `main.py`. `Router` создаётся в `__init__`, поэтому повторный вызов `get_router` продублирует все регистрации — вызывать его можно один раз.

Инстанс `Bot` попадает в хендлеры двумя разными способами: `ProfileSearchHandlers` и `AdminHandlers` получают его через `set_bot_instance()` из `main.py` (отсюда проверки `if not self.bot`), а `CommandHandlers` берёт из `message.bot`. Второй способ правильный — aiogram сам передаёт `bot` в хендлер; при рефакторинге этих классов сеттер можно убрать.

**`UserContextMiddleware` зарегистрирован как `outer_middleware` намеренно.** Inner-middleware выполняется уже после фильтрации, поэтому только outer успевает положить пользователя в контекст до фильтров. Фильтры получают его в аргументе `user`, потому что aiogram передаёт значение из `data` в параметр фильтра **с тем же именем** — связь держится на совпадении строки `"user"`, и при переименовании ключа фильтры молча уйдут в резервную ветку с запросом к БД (поведение сохранится, просядет только производительность). Потребители — `IsRegistered` и `IsFeedbackForCurrentProfile`; `IsAdmin` в БД не ходит вообще. Резервный путь с запросом к БД в фильтрах не убирай: он спасает, когда `user` пришёл `None` из-за недоступности БД.

**Порядок включения роутеров в `main.py` значим** — aiogram резолвит их в порядке подключения, и первое совпадение останавливает поиск. Отсюда два правила, которые надо держать при любой правке хендлеров:

- **Каждый текстовый хендлер состояния закрыт фильтром `not_command` (`~F.text.startswith("/")`)** — во всех роутерах, не только в регистрации. Без него состояние роутера, подключённого выше, съедает команды роутеров ниже: `/start` на шаге города записался бы как название города, `/searchi` во время смены имени стал бы новым именем, а любая команда в состоянии админской рассылки уехала бы текстом всем пользователям. Добавляешь новое текстовое состояние — добавляй и этот фильтр.
- **Fallback-хендлеры** («пришлите текст», «нажмите кнопку») регистрируются **после** основных хендлеров того же состояния, иначе перехватывают корректный ввод. Ловят они только нетекстовые сообщения, чтобы команды по-прежнему проваливались дальше по цепочке роутеров.

Побочный эффект: неизвестная команда внутри состояния не обрабатывается никем и бот молчит. Это принятый компромисс — закрывается общим catch-all в командном роутере, если понадобится.

FSM хранится в Redis, поэтому состояния переживают перезапуск бота, но теряются при очистке Redis. Группы состояний: `Register` (10 шагов анкеты, `handlers/registration.py`), `ChangeProfileStates` (редактирование, `profile_management.py`), `ProfileSearchStates` (просмотр анкет, сообщение, жалоба, `profile_search.py`), `CommandsStates` (текст в поддержку, `commands.py`), `AdminStates` (рассылка, `admin.py`).

`callback_data` собирается сырой склейкой префикса и `tg_chat_id`: `like<id>`, `dislike<id>`, `message<id>`, `complain<id>`, `yes<id>`, `no<id>`, а также `city_<название>` и `change_photo_one`/`add_photo_two`/`delete_photo_three`. Схема хрупкая, и её ловушки держатся на неочевидных страховках:

- **`"message"` — префикс `"message_to_all"`.** Хендлер анкеты висит на `F.data.startswith("message")` в роутере, который подключён раньше админского, поэтому кнопку рассылки «Message to all users» спасает только `StateFilter` на обоих хендлерах. Уберёшь состояние — админская рассылка перестанет открываться.
- **`"change_photo"` — префикс `"change_photo_one"`.** Разведено точным `F.data == "change_photo"`, зарегистрированным раньше `startswith`-варианта.
- **`"no"`** сейчас ни с чем не конфликтует, но `handle_yes_or_no_callback` зарегистрирован без `StateFilter` и перехватит любой будущий `none`/`notify_*` в любом состоянии.
- **`"like"` — суффикс `"dislike"`.** При `startswith` порядок проверок фактически не важен, но ветку `dislike` держат первой: порядок станет критичным, если проверка сменится на вхождение подстроки или на `removeprefix` без `startswith`.

При добавлении новых кнопок лучше заводить `CallbackData`-фабрику aiogram, чем наращивать префиксы.

### Модель данных

Таблицы (`db/sql_templates.sql`): `users`, `descriptions`, `stickers`, `likes`, `dislikes`, `messages`, `complains`. Неочевидное:

- `tg_chat_id` хранится **строкой** (`VARCHAR(20)`), а Telegram API отдаёт `int`. Код постоянно конвертирует туда-обратно: репозитории принимают `str`, хендлеры получают `int`. Это главный источник опечаток — сервисы приводят к `str` сами, поэтому в новые методы сервисов передавай `int`, а в репозитории `str`.
- Описание профиля лежит **не** в `users`, а в отдельной таблице `descriptions` 1:1. Поэтому `get_user_profile_data()` делает второй запрос и возвращает `None`, если описания нет.
- Фотографии — три отдельные колонки `photo_link`, `photo_link_two`, `photo_link_three`, и раскладка по «слотам» размазана по `user_service`, `profile_management` и `keyboards/inline`.
- `users.tg_username` объявлен `UNIQUE` — обновление занятого кем-то юзернейма даёт `UniqueViolation`, это учтено в middleware.
- `BaseRepository.get_by_id()` строит `WHERE id = $1`; у `users`, `likes`, `dislikes` такой колонки нет. `UserRepository` метод переопределяет, остальные его просто не вызывают.

### Подбор анкет

`MatchingService.get_profiles_for_user()` → `UserRepository.get_candidate_ids()` — **один** SQL-запрос: статус `yes`, исключение себя, диапазон возраста, пол (`Any` отключает фильтр), наличие описания, `NOT EXISTS` по `likes` и `dislikes`, `ORDER BY RANDOM() LIMIT`. Раньше здесь была выборка всех пользователей и по два запроса на каждого — не возвращайся к перебору в Python, добавляй условия в SQL.

Осознанные ограничения текущего подбора: город собирается, но в отборе **не участвует**; фильтрация односторонняя — учитываются только предпочтения ищущего, не встречные; дизлайк вечен, снять его нельзя. Асимметрия справочников: свой пол пишется как `Male/Female/Other`, а предпочитаемый — как `Male/Female/Any`, поэтому пользователя с `gender='Other'` найдёт только тот, кто выбрал `Any`. Список кандидатов перезапрашивается после каждого лайка (новый `RANDOM()`), так что «Профили закончились» означает «запрос вернул ноль строк», а не исчерпание какого-то курсора.

Индексов кроме первичных ключей в схеме нет, хотя взаимные лайки джойнят `likes` по `liked_chat_id` — на росте базы это первое место, где понадобится индекс.

ID показанной анкеты дублируется: `users.last_shown_profile` в БД (его читает фильтр `IsFeedbackForCurrentProfile`) и `shown_profile_id` в FSM-данных (его читают хендлеры). При правке этого места помни про оба места, они могут разойтись.

## Правила, которые легко нарушить

1. **Бот работает с `parse_mode="HTML"`.** Любой текст пользователя (имя, город, описание, причина жалобы, юзернейм) при подстановке в сообщение обязан идти через `escape()` из `utils/text.py`, иначе символ `<` или `&` даёт `TelegramBadRequest: can't parse entities`. Для пересылки чужого текста используй `message.html_text` — он сохраняет форматирование и экранирует остальное. `parse_mode="MARKDOWN"` не применяй: пользовательский текст с `*` или `_` ломает разбор.
2. **Отправка чему-либо другому пользователю — только через `utils/telegram.py`** (`safe_send_message`, `safe_send_media_group`, `safe_send_sticker`). Получатель мог заблокировать бота, и без перехвата `TelegramAPIError` падает весь сценарий инициатора.
3. **Никаких магических чисел** для возраста, длины имени/описания и числа фото — только `settings.*`. Минимальный возраст 18 стоит осознанно: это бот знакомств.
4. **SQL живёт только в репозиториях.** Сервисы и хендлеры не должны обращаться к `pool` напрямую (раньше `MatchingService` это делал).
5. Все состояния FSM должны иметь выход: если шаг ждёт текст — фильтр `F.text` плюс `not_command` плюс fallback на остальные типы; если ждёт кнопку — fallback на текст. Проверяй это имитацией роутинга, а не на глаз: состояние без выхода запирает пользователя молча.

## Чего в проекте нет

Чтобы не искать заново: **разговорных чатов по интересам, групповых чатов, комнат и тем — нет**, и никогда не было ни в одном коммите. Ближайшее существующее — одиночное сообщение анкете по кнопке «Message 💌» (таблица `messages`), это не групповой чат. Также нет: миграций схемы (только `CREATE TABLE IF NOT EXISTS`), тестов, линтеров, CI, rate-limiting кроме кулдауна `/support`, обработчика `dp.errors`. Метод `MessageRepository.get_messages_between_users` написан, но не используется — переписки внутри бота нет.

Мёртвые файлы, которые можно не изучать: `utils/filters.py`, `models/profile.py`, `keyboards/reply.py` (все пустые; действующие фильтры — в `filters/custom_filters.py`), каталог `data_base/` (остался только старый байт-код). В git закоммичены `__pycache__` от предыдущей архитектуры и `.idea/` — из индекса не убраны.
